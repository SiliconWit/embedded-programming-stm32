When an STM32 program does not start at all, the fault is often in code you did not write: the part that runs before `main()`. Most tutorials skip that part, so the first failure there can cost days. In this lesson you install the ARM toolchain, put a breathing LED program into the Blue Pill board, and follow the chip from its first read of memory after reset to your C code. #STM32 #ARM #Toolchain

## What We Are Building

<Card title="Breathing LED with HSE Clock and Timer PWM" icon="star">
An LED whose brightness rises and falls smoothly. PWM (pulse width modulation) sets the brightness: the pin switches on and off 1,000 times a second, and the fraction of each cycle that it is on (the duty cycle) sets how bright the LED looks. A timer, a hardware counter inside the chip, makes this signal, so the CPU is free. The PLL, a circuit that multiplies a clock, multiplies the 8 MHz board crystal (HSE, the high speed external clock) by 9 to give 72 MHz.
</Card>

### Connecting the ST-Link to the Blue Pill

The ST-Link V2 programs and debugs the chip through SWD (Serial Wire Debug), with four wires: data (SWDIO), clock (SWCLK), ground and 3.3V.

```text
  ST-Link V2            Blue Pill
  +----------+          +----------+
  | SWDIO ---+<-------->| SWDIO    |
  | SWCLK ---+--------->| SWCLK    |
  | GND -----+----------| GND      |
  | 3.3V ----+--------->| 3.3V     |
  +----------+          +----------+
    (USB to PC)       (STM32F103C8T6)
```

The Blue Pill has a 4-pin SWD header at the end of the board. Its small printed labels often read DIO for SWDIO and CLK for SWCLK.

Test the connection:

```bash
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg
```

You should see output ending with something like `Info : stm32f1x.cpu: hardware has 6 breakpoints, 4 watchpoints`. Press `Ctrl+C` to exit.

If OpenOCD cannot find `interface/stlink.cfg`, your version is 0.10: use `interface/stlink-v2.cfg`. If it reports `UNEXPECTED idcode: 0x2ba01477`, the board carries a copy of the chip (CKS32 or CS32): add `-c "set CPUTAPID 0x2ba01477"` before the target file.

## ARM Cortex-M3 Architecture Overview

<InArticleAd />


The STM32F103 is an ARM Cortex-M3 core, the processor, with memory and peripherals (timers, serial ports, pin drivers) that ST adds around it. Four ideas explain what happens before `main()`.

### Memory Map

The core reaches the program, the variables and the hardware through addresses, like houses numbered along one street. A **register** is a memory location that belongs to a peripheral: writing a number to it changes what the hardware does. So `TIM2->CCR1 = 500` is an ordinary write to address 0x4000_0034, which belongs to timer 2. The fixed regions:

| Address Range | Region | STM32F103 Usage |
|---------------|--------|-----------------|
| 0x0000_0000 to 0x1FFF_FFFF | Code | Flash at 0x0800_0000: keeps the program with power off |
| 0x2000_0000 to 0x3FFF_FFFF | SRAM | 20 KB for variables, lost with power off |
| 0x4000_0000 to 0x5FFF_FFFF | Peripherals | Registers of pins (GPIO), UART, SPI, timers |
| 0xE000_0000 to 0xE00F_FFFF | System | Registers of the core: interrupts, SysTick, debug |

### Vector Table

After reset the core does not know where your program is. It reads a list of addresses, the vector table, at 0x0000_0000, which shows the same memory as the start of flash (0x0800_0000) while the BOOT0 jumper is at 0. (At 1, ST's built-in loader runs instead of your program.) The first entry is the starting stack pointer; the stack is the RAM that holds local variables and return addresses, and no C function runs without it. The second is the address of the reset handler. The rest are the addresses of the fault and interrupt handlers. The hardware loads the first two before any code runs:

```text
  1. Read word at 0x0000_0000 --> MSP
     (main stack pointer: where the stack begins)

  2. Read word at 0x0000_0004 --> PC
     (program counter: jump to Reset_Handler)

  3. Reset_Handler runs (the startup code)
```

```c
/* Simplified vector table structure */
uint32_t vector_table[] = {
    (uint32_t)&_estack,        /* Initial stack pointer */
    (uint32_t)Reset_Handler,   /* Reset handler */
    (uint32_t)NMI_Handler,     /* Non-maskable interrupt */
    (uint32_t)HardFault_Handler, /* Hard fault */
    /* ... more exception handlers ... */
    (uint32_t)TIM2_IRQHandler, /* TIM2 global interrupt */
    /* ... more peripheral interrupts ... */
};
```

### Startup Code

The reset handler is the startup code. C expects global variables to be ready when `main()` begins, but after power-on RAM holds nothing useful. So the startup code:

1. Calls `SystemInit()` from the device files (in current ST files it only sets where the vector table is). No global variable is ready yet.
2. Copies the starting values of initialized globals from flash, which keeps them without power, to RAM, where the program can change them (the `.data` section).
3. Fills with zero the globals that have no starting value (the `.bss` section).
4. Calls the C library's start code (`__libc_init_array()`), then `main()`.

### Linker Script

The compiler does not know this chip's memory. The linker script gives the start and size of flash and RAM, and which part of the program goes where:

```ld
/* Minimal STM32F103C8T6 linker script excerpt */
MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 64K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 20K
}

SECTIONS
{
    .isr_vector : {
        KEEP(*(.isr_vector))
    } > FLASH

    .text : {
        *(.text*)
        *(.rodata*)
    } > FLASH

    _sidata = LOADADDR(.data);   /* where the starting values sit in flash */
    .data : {
        _sdata = .;
        *(.data*)
        _edata = .;
    } > RAM AT > FLASH

    .bss : {
        _sbss = .;
        *(.bss*)
        _ebss = .;
    } > RAM
}

_estack = ORIGIN(RAM) + LENGTH(RAM);
```

The last line is the first entry of the vector table: the end of RAM, 0x2000_0000 + 20 KB = 0x2000_5000. The stack starts there and grows downward. The startup code finds what to copy and what to zero through the names `_sidata` to `_ebss`. For the build, take ST's complete `STM32F103XB_FLASH.ld` (STM32CubeF1, `Drivers/CMSIS/Device/ST/STM32F1xx/Source/Templates/gcc/linker/`), save it as `STM32F103C8Tx_FLASH.ld` and set flash to 64K.

### Clock Configuration (HSE + PLL = 72 MHz)

Every digital circuit in the chip moves one step on each tick of a clock, a signal at a fixed frequency. After reset the chip runs from an internal 8 MHz oscillator that is not very accurate. We select the accurate 8 MHz crystal on the HSE pins and let the PLL multiply it by 9: a 72 MHz system clock (SYSCLK), the maximum for this chip.

```text
  HSE crystal     PLL        SYSCLK
  +-------+    +------+    +--------+
  | 8 MHz |--->|  x9  |--->| 72 MHz |
  +-------+    +------+    +---+----+
                               |
                      AHB bus, /1: 72 MHz
                               |
              +----------------+---------+
              |                          |
     APB2 bus, /1: 72 MHz     APB1 bus, /2: 36 MHz
     GPIO, SPI1, USART1       TIM2-4, I2C, USART2
```

A bus is a set of internal lines that carries a clock and data to a group of peripherals. The AHB bus serves the core and the memory. From it branch APB2 at 72 MHz and APB1, whose peripherals must not run above 36 MHz, so its clock is divided by 2. A divider is called a prescaler.

One rule surprises most people: when the APB1 clock is divided, the chip doubles the clock it gives to the timers on that bus. So TIM2 counts from 72 MHz, and the timer code below depends on this.

In the code, each wait is for a ready bit. The crystal can fail (a bad joint), so its wait has a limit: the function returns and the chip stays on the internal 8 MHz clock.

```c
void clock_init(void) {
    /* Enable HSE (external 8 MHz crystal); it needs about 2 ms */
    RCC->CR |= RCC_CR_HSEON;
    for (uint32_t t = 0; !(RCC->CR & RCC_CR_HSERDY); t++) {
        if (t > 200000) return;   /* no crystal: stay on the 8 MHz HSI */
    }

    /* Configure flash latency for 72 MHz (2 wait states, LATENCY = 010) */
    FLASH->ACR |= FLASH_ACR_LATENCY_1;  /* Bit 1 of the field = value 2 */

    /* Configure PLL: HSE as source, multiply by 9 = 72 MHz */
    RCC->CFGR |= RCC_CFGR_PLLSRC;       /* HSE as PLL source */
    RCC->CFGR |= RCC_CFGR_PLLMULL9;     /* PLL x9 */

    /* AHB prescaler = 1, APB1 prescaler = 2, APB2 prescaler = 1 */
    RCC->CFGR |= RCC_CFGR_PPRE1_DIV2;

    /* Enable PLL and wait for it to lock */
    RCC->CR |= RCC_CR_PLLON;
    while (!(RCC->CR & RCC_CR_PLLRDY));

    /* Switch system clock to PLL */
    RCC->CFGR |= RCC_CFGR_SW_PLL;
    while ((RCC->CFGR & RCC_CFGR_SWS) != RCC_CFGR_SWS_PLL);
}
```

### Timer PWM Setup

The first two lines switch on the clocks of port A and TIM2: a peripheral without a clock ignores every write. Three registers then set the signal:

- `PSC` (prescaler) divides the 72 MHz timer clock by 72, so the counter advances once each microsecond.
- `ARR` (auto-reload) is the value at which the counter returns to zero. Counting 0 to 999 takes 1,000 microseconds, so the signal repeats at 1 kHz.
- `CCR1` (compare) sets the brightness. The pin is high while the counter is below `CCR1`, so `CCR1 = 250` keeps the LED on for 25% of each cycle.

`PSC` and `ARR` are written as the wanted number minus 1, because the hardware counts from 0.

```c
void pwm_init(void) {
    /* Enable GPIOA and TIM2 clocks */
    RCC->APB2ENR |= RCC_APB2ENR_IOPAEN;
    RCC->APB1ENR |= RCC_APB1ENR_TIM2EN;

    /* PA0 as alternate function push-pull output */
    GPIOA->CRL &= ~(0xF << 0);
    GPIOA->CRL |= (0xB << 0);  /* AF push-pull, 50 MHz */

    /* TIM2 configuration: 1 kHz PWM */
    TIM2->PSC = 72 - 1;       /* 72 MHz / 72 = 1 MHz timer clock */
    TIM2->ARR = 1000 - 1;     /* 1 MHz / 1000 = 1 kHz PWM */
    TIM2->CCR1 = 0;           /* Start with 0% duty cycle */

    /* PWM mode 1 on channel 1, preload enable */
    TIM2->CCMR1 |= (0x6 << 4) | TIM_CCMR1_OC1PE;
    TIM2->CCER |= TIM_CCER_CC1E;  /* Enable CH1 output */
    TIM2->CR1 |= TIM_CR1_CEN;     /* Start timer */
}
```

### Main Loop (Breathing Effect)

The loop changes `CCR1` by one count on each pass, from 0 up to 999 and down again. The timer also keeps the time: it sets its update flag `UIF` at the end of each 1 ms period, and the loop waits for it. One breath is 999 steps up and 999 down, 1,998 ms. An empty counting loop would give a time that changes with the compiler settings.

```c
#include "stm32f103xb.h"

void clock_init(void);
void pwm_init(void);

int main(void) {
    clock_init();
    pwm_init();

    uint16_t brightness = 0;
    int8_t direction = 1;

    while (1) {
        TIM2->CCR1 = brightness;

        brightness += direction;
        if (brightness >= 999) {
            direction = -1;
        } else if (brightness == 0) {
            direction = 1;
        }

        /* Wait for the end of this 1 ms PWM period, then clear the flag
           (the SysTick timer takes this job when you build the menu) */
        while (!(TIM2->SR & TIM_SR_UIF));
        TIM2->SR = ~TIM_SR_UIF;
    }
}
```

### Makefile

```makefile
TARGET = breathing-led
CC = arm-none-eabi-gcc
OBJCOPY = arm-none-eabi-objcopy

CFLAGS = -mcpu=cortex-m3 -mthumb -Os -Wall -g
CFLAGS += -DSTM32F103xB
CFLAGS += -Iinclude

# nano.specs: the small C library; nosys.specs: no operating system
LDFLAGS = -T STM32F103C8Tx_FLASH.ld --specs=nano.specs --specs=nosys.specs
LDFLAGS += -Wl,--gc-sections

SRCS = src/main.c src/system_stm32f1xx.c src/startup_stm32f103.s

all: $(TARGET).bin

$(TARGET).elf: $(SRCS)
	$(CC) $(CFLAGS) -o $@ $^ $(LDFLAGS)

$(TARGET).bin: $(TARGET).elf
	$(OBJCOPY) -O binary $< $@

flash: $(TARGET).bin
	openocd -f openocd.cfg -c "program $< 0x08000000 verify reset exit"

clean:
	rm -f $(TARGET).elf $(TARGET).bin

.PHONY: all flash clean
```


`make flash` writes the program at 0x0800_0000, the start of flash. The LED on PA0 should now rise and fall smoothly. If it blinks instead, check the PA0 wiring and the timer configuration.

### Check it

"It breathes" does not prove the clock is right. Two checks do:

1. Time ten breaths with a phone stopwatch: about 20 s. About 180 s means the crystal did not start, so the timer counts from 8 MHz instead of 72 MHz.
2. Hold `TIM2->CCR1 = 500;` for a moment and measure PA0 to GND with a multimeter (DC volts): about 1.65 V, half of 3.3 V. A Hz range reads 1,000 Hz (111 Hz: no crystal). 0 V or 3.3 V means the timer is not driving the pin: check the clock enables and `CRL`.

## Exploring with STM32CubeMX

<InArticleAd />


STM32CubeMX generates setup code for clocks, peripherals and pins with HAL (hardware abstraction layer), ST's library of ready functions. It also shows which pin can carry which signal.

<Steps>
1. Open STM32CubeMX and create a new project for STM32F103C8T6.

2. Click the **Clock Configuration** tab. Set HSE to 8 MHz, enable PLL, set the multiplier to x9, and check that the system clock shows 72 MHz and APB1 shows 36 MHz.

3. Back in the **Pinout** tab, click PA0 and set it to TIM2_CH1. The pin turns green when the assignment is valid.

4. Under **Timers > TIM2**, set Channel 1 to "PWM Generation CH1". Set the prescaler and auto-reload to our values for 1 kHz.

5. Click **Generate Code** and compare the generated `MX_TIM2_Init()` with our code. The same registers are written; HAL wraps them in structures and error checks.
</Steps>

## CMSIS and Device Headers

<InArticleAd />


CMSIS (Cortex Microcontroller Software Interface Standard) is a set of files that gives each of the hundreds of registers a name. With the device header (`stm32f103xb.h`) you write `TIM2->CCR1` instead of `*(volatile uint32_t*)0x40000034`. Two sources for the headers:

- The STM32CubeF1 package: clone `https://github.com/STMicroelectronics/STM32CubeF1`. The headers are in `Drivers/CMSIS/Device/ST/STM32F1xx/Include/`.
- CubeMX: when you generate code, it copies the headers into your project.
