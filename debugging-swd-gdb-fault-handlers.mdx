A board works on the bench for ten seconds and then stops, silently, because the code that prints has stopped too. Reading the source again does not help: the line where a program stops is often not the line with the mistake. A debugger lets you stop the processor, look inside its memory and see what happened. In this lesson you connect the GDB debugger to the chip, learn the tools the Cortex-M3 processor gives you, and then find five bugs planted in a firmware project. #STM32 #Debugging #GDB

## What We Are Building

<Card title="Bug Hunt Challenge: Find and Fix Five Bugs" icon="star">
A firmware project with five planted bugs, each of a kind you will meet in real work: a pointer that points at nothing, a function that calls itself without end, a peripheral with a wrong setting, two pieces of code that write the same memory at the same time, and a loop that waits for ever. You find and fix each one with GDB.
</Card>

## Setting Up GDB with OpenOCD

<InArticleAd />


### Starting OpenOCD

Three parts work together. GDB is the debugger on your computer, where you type commands. The ST-Link is the USB probe, joined to the chip by the two SWD (Serial Wire Debug) wires. OpenOCD sits between them and turns GDB requests into USB messages for the ST-Link.

```text
  +-------+            +---------+  USB  +--------+
  |  GDB  |<---------->| OpenOCD |<----->| ST-Link|
  | (PC)  | port 3333  | (PC)    |       | V2     |
  +-------+            +---------+       +---+----+
                                             |
                                          SWD (2 wires)
                                             |
                                         +---+------+
                                         | STM32    |
                                         | Cortex-M3|
                                         | (target) |
                                         +----------+
```

```bash
# Terminal 1: Start OpenOCD
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg
```

OpenOCD listens on port 3333 for GDB connections and port 4444 for a telnet command interface.

### Connecting GDB

Give GDB the `.elf` file, not the `.bin`: it also holds the names of functions and variables and the line numbers, so GDB can show source lines where the chip has only addresses.

```bash
# Terminal 2: Start GDB
arm-none-eabi-gdb firmware.elf

# Or if using gdb-multiarch (common on Ubuntu)
gdb-multiarch firmware.elf
```

Inside GDB:

```gdb
# Connect to OpenOCD
target remote localhost:3333

# Load firmware into flash
monitor reset halt
load

# Set a breakpoint at main
break main

# Start execution
continue
```

### Essential GDB Commands

| Command | Short | Description |
|---------|-------|-------------|
| `break main` | `b main` | Set breakpoint at function |
| `break *0x08001234` | `b *0x08001234` | Breakpoint at address |
| `continue` | `c` | Resume execution |
| `step` | `s` | Step one source line (into functions) |
| `next` | `n` | Step one source line (over functions) |
| `stepi` | `si` | Step one instruction |
| `print var` | `p var` | Print variable value |
| `print/x var` | `p/x var` | Print in hexadecimal |
| `info registers` | `i r` | Show all CPU registers |
| `info breakpoints` | `i b` | List breakpoints |
| `backtrace` | `bt` | Show call stack |
| `watch var` | | Break when variable changes |
| `x/16xw 0x20000000` | | Examine 16 words at address |
| `monitor reset halt` | | Reset and halt the MCU |

## Breakpoints and Watchpoints

<InArticleAd />


A breakpoint is a stop sign at a chosen place in the code: use it when you know where to look. A watchpoint is an alarm on a chosen piece of memory, which stops the processor when anything reads or writes it: use it when you know which variable is wrong but not which code changes it.

The Cortex-M3 has 6 hardware breakpoints and 4 hardware watchpoints. They are comparators inside the processor, so they work on code in flash without changing it, and you cannot set more than 6 breakpoints at once.

### Using Breakpoints

```gdb
# Break when entering uart_send_string
break uart_send_string

# Conditional breakpoint: only when adc_value > 3000
break main.c:85 if adc_values[0] > 3000

# Temporary breakpoint (deleted after first hit)
tbreak process_command

# Delete all breakpoints
delete
```

### Using Watchpoints

```gdb
# Break when 'counter' variable is written
watch counter

# Break when 'counter' is read
rwatch counter

# Break when memory at specific address is written
watch *(uint32_t*)0x20000100

# Useful for finding who corrupts a specific variable
watch stack_canary
```

### Examining Memory

```gdb
# Examine the stack (16 32-bit words at current SP)
x/16xw $sp

# Examine the vector table
x/16xw 0x08000000

# Examine a peripheral register (e.g., RCC->CR)
x/xw 0x40021000

# Examine a struct
print *((GPIO_TypeDef*)0x40010800)
```

## HardFault Decoding

<InArticleAd />


Some instructions cannot be carried out: a read from an address with no memory, a code that is not an instruction, a division by zero when that check is on. The Cortex-M3 then jumps to the HardFault handler. The default handler is an empty loop, so without your own the board only seems dead.

Before it jumps, the processor saves eight registers on the stack (the RAM that holds return addresses and local variables). One is the program counter (PC), the address of the instruction that failed. Each takes 4 bytes, so the saved PC, register number 6, is 24 bytes above the stack pointer (SP).

```text
  higher address
  +------+
  | xPSR |  SP + 28   stack_frame[7]
  | PC   |  SP + 24   stack_frame[6]  <- failed here
  | LR   |  SP + 20   stack_frame[5]
  | R12  |  SP + 16   stack_frame[4]
  | R3   |  SP + 12   stack_frame[3]
  | R2   |  SP + 8    stack_frame[2]
  | R1   |  SP + 4    stack_frame[1]
  | R0   |  SP + 0    stack_frame[0]
  +------+
  lower address: SP when the handler starts
```

LR (the link register) holds the address the failed function would have returned to, so it tells you who called it.

### HardFault Handler

Four lines of assembly find which stack pointer was in use (MSP for the main program, PSP for tasks under an operating system) and pass it to a C function, which copies the saved registers into variables that GDB can print.

```c
__attribute__((naked)) void HardFault_Handler(void) {
    __asm volatile (
        "TST   LR, #4          \n"  /* Check which stack was in use */
        "ITE   EQ               \n"
        "MRSEQ R0, MSP          \n"  /* Main stack pointer */
        "MRSNE R0, PSP          \n"  /* Process stack pointer */
        "B     hard_fault_handler_c \n"
    );
}

void hard_fault_handler_c(uint32_t *stack_frame) {
    volatile uint32_t r0  = stack_frame[0];
    volatile uint32_t r1  = stack_frame[1];
    volatile uint32_t r2  = stack_frame[2];
    volatile uint32_t r3  = stack_frame[3];
    volatile uint32_t r12 = stack_frame[4];
    volatile uint32_t lr  = stack_frame[5];
    volatile uint32_t pc  = stack_frame[6];  /* Faulting instruction */
    volatile uint32_t psr = stack_frame[7];

    /* Configurable Fault Status Register */
    volatile uint32_t cfsr = SCB->CFSR;
    volatile uint32_t hfsr = SCB->HFSR;
    volatile uint32_t mmfar = SCB->MMFAR;  /* Memory fault address */
    volatile uint32_t bfar = SCB->BFAR;    /* Bus fault address */

    /* Suppress unused variable warnings */
    (void)r0; (void)r1; (void)r2; (void)r3;
    (void)r12; (void)lr; (void)pc; (void)psr;
    (void)cfsr; (void)hfsr; (void)mmfar; (void)bfar;

    /*
     * In GDB, set a breakpoint here and examine:
     *   print/x pc    -> address of faulting instruction
     *   print/x lr    -> return address (caller)
     *   print/x cfsr  -> fault type bits
     *   info line *pc -> source file and line number
     */

    while (1);  /* Halt here for debugger */
}
```

### CFSR Bit Decoding

The saved PC says where the program failed. The Configurable Fault Status Register (CFSR) says why. Its 32 bits are three smaller registers side by side, one for each kind of fault. A bit whose name ends in VALID means that the address the program tried to use is stored in MMFAR or BFAR.

| Bit Range | Register | Key Bits |
|-----------|----------|----------|
| [7:0] | MMFSR (MemManage) | MMARVALID, DACCVIOL, IACCVIOL |
| [15:8] | BFSR (BusFault) | BFARVALID, PRECISERR, IMPRECISERR |
| [31:16] | UFSR (UsageFault) | UNDEFINSTR, INVSTATE, INVPC, UNALIGNED |

### Debugging a HardFault in GDB

```gdb
# When the firmware hits the HardFault handler:
break hard_fault_handler_c

# After it breaks, examine the saved PC (faulting instruction)
print/x stack_frame[6]

# Look up which source line that address corresponds to
info line *0x08001A3C

# Examine the fault status registers
print/x *(uint32_t*)0xE000ED28    # CFSR
print/x *(uint32_t*)0xE000ED2C    # HFSR

# Examine the faulting address (if MemManage or BusFault)
print/x *(uint32_t*)0xE000ED34    # MMFAR
print/x *(uint32_t*)0xE000ED38    # BFAR
```

## ITM Trace Output

<InArticleAd />


Printed messages are still useful, but a UART is slow and your product may need every UART it has. The ITM (Instrumentation Trace Macrocell) in the processor sends bytes to the debug probe through one extra pin, SWO (Serial Wire Output). It uses no UART and changes the program timing very little.

```text
  firmware            inside the chip
  +--------------+    +-----+    +------+
  | ITM->PORT[0] |--->| ITM |--->| TPIU |
  +--------------+    +-----+    +--+---+
                                    | SWO pin (PB3)
                                    v
  +---------------+   +---------+   +---------+
  | /tmp/itm.fifo |<--| OpenOCD |<--| ST-Link |
  +---------------+   +---------+   +---------+
```

The program writes a byte to an ITM port. The TPIU (Trace Port Interface Unit) sends it out on SWO, which is pin PB3 on the Blue Pill. OpenOCD writes what arrives to a file. Many low-cost ST-Link clones do not connect SWO: if yours has no SWO pin on its connector, ITM gives no output.

### ITM Printf

```c
/* Send a character via ITM stimulus port 0 */
void itm_putc(char c) {
    /* Skip if no debugger has enabled ITM and port 0 (avoids a hang) */
    if (!(ITM->TCR & ITM_TCR_ITMENA_Msk) || !(ITM->TER & 1UL)) return;
    while (ITM->PORT[0].u32 == 0);  /* Wait until port is ready */
    ITM->PORT[0].u8 = (uint8_t)c;
}

void itm_puts(const char *str) {
    while (*str) {
        itm_putc(*str++);
    }
}
```

### OpenOCD ITM Configuration

```bash
# In the OpenOCD telnet console (port 4444):
# Enable SWO trace at 72 MHz core clock, 2 MHz SWO baud
tpiu config internal /tmp/itm.fifo uart off 72000000 2000000

# Enable stimulus port 0
itm port 0 on
```

```bash
# In a separate terminal, read the ITM output:
cat /tmp/itm.fifo
```

## Bug Hunt: The Five Bugs

<InArticleAd />


Each bug below has a symptom and a way to approach it. The solutions follow.

### Bug 1: HardFault on Peripheral Enable

**Symptom:** The firmware crashes immediately after calling `sensor_init()`.

**Debugging approach:**
<Steps>
1. Set a breakpoint at `sensor_init()` and step through line by line.
2. When the HardFault triggers, examine the saved PC register in the fault handler.
3. Look up the source line with `info line *<PC>`.
4. Check: is the code dereferencing a pointer? Is that pointer valid?
</Steps>

### Bug 2: Serial Output Stops After 10 Seconds

**Symptom:** The serial terminal shows data for about 10 seconds, then output freezes. The MCU does not reset, it just hangs.

**Debugging approach:**
<Steps>
1. Let the firmware run until output stops.
2. Press Ctrl+C in GDB to halt the CPU.
3. Run `backtrace` to see where the CPU is stuck.
4. The stack starts at the top of RAM (`0x20005000` on this chip) and grows down. If the backtrace shows the same function hundreds of times, or SP is near the bottom of RAM (`0x20000000`), the stack has grown into your variables. This is a stack overflow.
5. Check for recursive functions or large local arrays.
</Steps>

### Bug 3: ADC Readings Always Zero

**Symptom:** The ADC values displayed on serial are always 0 for all channels.

**Debugging approach:**
<Steps>
1. Check if the ADC clock is enabled: `x/xw 0x40021018` (RCC->APB2ENR).
2. Check if the ADC is powered on: `x/xw 0x40012408` (ADC1->CR2).
3. Check the DMA buffer: `x/3hx &adc_values`.
4. Compare the ADC configuration registers with the working code from the ADC and DMA lesson.
</Steps>

### Bug 4: OLED Shows Corrupted Data

**Symptom:** The OLED display usually looks correct but occasionally shows garbled pixels or shifted text.

**Debugging approach:**
<Steps>
1. Set a watchpoint on the framebuffer: `watch framebuffer[0]`.
2. Check if DMA and the main loop are both writing to the framebuffer simultaneously.
3. Look for missing DMA completion checks before modifying the buffer.
</Steps>

### Bug 5: System Resets Every ~4 Seconds

**Symptom:** The firmware runs for about 4 seconds, then resets. The reset cause register (RCC->CSR) shows a watchdog reset. A watchdog is a timer that resets the chip unless the program restarts it ("feeds" it) in time, so that a program that hangs does not stay hung.

**Debugging approach:**
<Steps>
1. Search the code for IWDG (Independent Watchdog) initialization.
2. Check if the watchdog is being fed (refreshed) regularly.
3. Look for blocking loops or long delays that prevent the watchdog refresh.
</Steps>

## Solutions

<InArticleAd />


:::caution[Try finding the bugs yourself first]
The solutions below give the cause and the fix for each bug. You learn most when you find them with the debugger yourself, so read these only after you have tried.
:::

### Bug 1 Solution: Null Pointer Dereference

The `sensor_init()` function receives a pointer to a configuration struct, but the caller passes `NULL`:

```c
/* Bug: passing NULL */
sensor_config_t *config = NULL;
sensor_init(config);  /* Dereferences config->i2c_addr, causing HardFault */

/* Fix: initialize the struct */
sensor_config_t config = { .i2c_addr = 0x76, .oversample = 1 };
sensor_init(&config);
```

### Bug 2 Solution: Unbounded Recursion

A logging function calls itself recursively when the log buffer is full, instead of dropping the message:

```c
/* Bug: recursive call without base case */
void log_message(const char *msg) {
    if (log_buf_full()) {
        log_flush();
        log_message(msg);  /* Stack grows each time if flush fails */
    }
    /* ... */
}

/* Fix: flush once, then drop the message instead of recursing */
void log_message(const char *msg) {
    if (log_buf_full()) {
        log_flush();
        if (log_buf_full()) return;  /* Drop message if still full */
    }
    /* ... */
}
```

### Bug 3 Solution: Missing ADC Clock Enable

The ADC clock enable line is commented out or uses the wrong register bit:

```c
/* Bug: enabling SPI1 clock instead of ADC1 */
RCC->APB2ENR |= RCC_APB2ENR_SPI1EN;

/* Fix: enable ADC1 clock */
RCC->APB2ENR |= RCC_APB2ENR_ADC1EN;
```

### Bug 4 Solution: DMA Race Condition

A race condition is a fault that depends on which of two activities reaches shared data first. Here the main loop changes the framebuffer (the array that holds the picture) while DMA is still sending the previous picture from it:

```c
/* Bug: no synchronization */
oled_clear();           /* Writes to framebuffer */
draw_dashboard();       /* Writes to framebuffer */
oled_update_dma();      /* Starts DMA transfer */
/* Main loop immediately starts modifying framebuffer again */

/* Fix: wait for DMA transfer to complete before modifying buffer */
while (spi_dma_busy);   /* Wait for previous transfer */
oled_clear();
draw_dashboard();
oled_update_dma();
```

### Bug 5 Solution: Blocking Loop Starves Watchdog

A sensor read function has a blocking wait for a "data ready" flag that never gets set because the sensor was not properly configured:

```c
/* Bug: infinite wait if sensor not configured */
while (!(i2c_read_reg(BME280_ADDR, 0xF3) & 0x08));  /* Wait for data ready */

/* Fix: add timeout */
uint32_t start = systick_ms;
while (!(i2c_read_reg(BME280_ADDR, 0xF3) & 0x08)) {
    if ((systick_ms - start) > 100) {
        return SENSOR_TIMEOUT;  /* Bail out after 100 ms */
    }
    iwdg_feed();  /* Keep watchdog alive while waiting */
}
```
